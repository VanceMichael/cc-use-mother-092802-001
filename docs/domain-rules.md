# 领域边界

管理人工智能模型、数据和算力资源的申请、评审、配额与公平开放。

现有领域资料围绕以下边界组织：

- 资源与许可版本
- 申请评审
- 算力配额守恒
- 敏感信息裁剪
- 公平性解释

资料版本只能递增。参与方、事实和约束均不能为空，示例不得包含真实个人信息、账号或凭据。

# 资源开放服务领域规则（v2）

本节把资源开放服务的业务要求固化为编号规则。所有规则均由 `src/` 下的代码实现，并由
`tests/test_resource_service.py` 逐条验证。规则编号格式为 `R-<域>-<号>`。

## 1. 参与方与对象

参与方：社区运营人员、央企资源提供方、开发者、安全审核人员、行业场景负责人。

核心对象及其关联：

- 机构（organization）：开发者所属单位，分属不同群体（如工业一线、科研院所、中小团队）。
- 开发者（developer）：自然人申请人，隶属机构。
- 项目目标（project）：申请所服务的项目及其行业场景（工业一线 / 安全研究 / 公共服务）。
- 资源版本（resource revision）：模型或数据集的某个版本，携带许可范围与敏感等级。
- 申请版本（application revision）：同一申请键下内容不可变的版本序列。
- 评审决定（decision）：批准、拒绝或例外批准，记录所依据的规则版本。
- 配额池（quota pool）：某算力资源在某周期内的可分配总量。
- 额度（grant）：批准产生的算力额度，可领取、释放、延期。
- 授权访问（access grant）：对敏感数据/模型的访问授权，有到期时间。

## 2. 连续记录：只追加事件台账（R-LOG）

- R-LOG-1：所有事实以事件表达，事件只能追加、不能修改或删除（append-only）。
- R-LOG-2：每条事件含单调递增序号、时间戳、类型、载荷、前一条事件的哈希；
  首条事件的前哈希为固定空值。任一事件被改动，其后所有哈希校验失败。
- R-LOG-3：序号与时间戳均单调不减；同一序号在同一台账内唯一。
- R-LOG-4：机构、开发者、项目目标、资源版本、许可、算力需求、评审依据、实际用量
  全部以事件落账，可从台账重放出任一时刻的完整状态（见 `src/projections.py`）。

## 3. 差异化规则与规则版本（R-RULE）

- R-RULE-1：工业一线、安全研究、公共服务项目采用不同规则集（准入条件、额度上限、
  是否允许敏感资源、例外条件等）。
- R-RULE-2：规则按版本发布，版本号只能递增；规则变更生成新版本，不覆盖旧版本。
- R-RULE-3：规则变化只影响**尚未作出**的决定。每条评审决定记录作出时生效的
  规则版本（decided-under）；已获批额度永久保留当时依据，不因规则升级而被重判、
  缩减或撤销（无追溯力）。
- R-RULE-4：规则发布事件在其生效时间之前不得被任何评审引用。

## 4. 申请幂等与版本化（R-APP）

- R-APP-1：每个申请有稳定申请键（申请人 + 项目 + 资源 + 周期的确定性摘要）。
- R-APP-2：以同一申请键重复申请，若提交内容的指纹未变，返回**原申请版本与原评审结果**，
  不产生新事件、不重新评审（幂等）。
- R-APP-3：同一申请键下提交内容发生变化（模型/数据集版本、算力需求、用途等），
  产生**新的不可变申请版本**；新版本独立走评审，旧版本及其决定保持可查。
- R-APP-4：对已经有"批准"决定的申请版本，不允许再作决定；撤回后重新提交属于新版本。

## 5. 评审职责隔离（R-REV）

- R-REV-1：申请人不能参与本人申请的任何评审，例外批准同样禁止（self-review 拒绝）。
- R-REV-2：评审人员只能查看**履职所需**资料（need-to-know / 最小知情）：
  - 普通评审默认不暴露敏感数据集的存在；
  - 安全审核人员评审安全研究申请时，可见安全专区资源的存在与许可，但仍不展开
    超出该申请所需的其他敏感资源；
  - 与评审职责无关的字段（如开发者的其他项目、内部配额余量）不下发。
- R-REV-3：评审决定必须附依据：引用的规则版本、条款、命中/不命中事实。
- R-REV-4：例外（放宽规则条款）须由非申请人的第二评审人复核，记录双签。

## 6. 存在性隐藏（R-PRIV）

- R-PRIV-1：无权人员不能通过**搜索、列表、错误提示或聚合结果**推断敏感数据是否存在。
  对无权方，敏感资源在搜索中不可见、按标识直取返回与"不存在"不可区分的结果。
- R-PRIV-2：计数、用量、公平性等聚合统计对敏感资源做脱敏：敏感资源的占用
  并入不暴露其身份的桶（如"安全专区资源"），或在样本不足时抑制明细。
- R-PRIV-3：访问授权到期或撤销后，对应资源对该人恢复为不可见。

## 7. 算力配额守恒（R-QUOTA）

- R-QUOTA-1：任一周期，任一刻满足
  `已分配 + 已领取占用 + 已核对用量 ≤ 池容量`；超容量分配被拒绝。
- R-QUOTA-2：额度操作守恒：
  - 领取（claim）把额度从"已分配待领取"转入"已领取占用"，总量不变；
  - 释放（release）把未用部分退回池容量（可再分配），并记录释放量；
  - 延期（extend）只改到期时间，不新增任何算力单位；需要更多额度必须新申请；
  - 用量核对（usage report）只在已领取额度内扣减，不得为负、不得超出。
- R-QUOTA-3：拒绝不占用任何配额；批准即预留，预留超时未领取可由停机接续任务回收。
- R-QUOTA-4：并发或重复提交同一额度指令以指令幂等键去重，余额不发生重复变动。

## 8. 停机接续（R-RESUME）

服务停机后重启，仅凭台账即可接续全部在途工作，不依赖内存状态：

- R-RESUME-1：即将到期的访问授权与额度触发续期/到期处理（到期自动失效并释放预留）。
- R-RESUME-2：未完成评审（已提交、待决定）重新进入评审队列。
- R-RESUME-3：停机期间窗口已过的事件，在重启重放时按其业务时间补处理，结果与
  连续在线等价（重放确定性）。
- R-RESUME-4：用量核对以台账中已记录的领取/释放为边界对账，重复上报按幂等键忽略。

## 9. 可解释（R-EXPLAIN）

运营人员对任一项目可取得一次批准/拒绝的完整解释：

- R-EXPLAIN-1：依据的规则版本与具体条款、命中事实；
- R-EXPLAIN-2：使用的是哪一版模型 / 数据集（资源版本标识与许可范围）；
- R-EXPLAIN-3：获得的额度来自哪个配额池、批准时池余量、同期被拒/排队的申请，
  用以说明**是否挤占他人额度**；
- R-EXPLAIN-4：解释内容由台账重放生成，不可手工编辑。

## 10. 公平开放度量（R-FAIR）

- R-FAIR-1：按开发者所属群体（机构类型/行业场景/规模）统计申请量、批准率、
  平均等待、满足率（实批/申请算力）与到期前可续期率。
- R-FAIR-2：度量基于"决定作出时的规则版本与池状态"，规则变更前后分段统计，
  避免把规则变化误记为群体待遇变化。
- R-FAIR-3：涉及敏感资源的明细按 R-PRIV-2 脱敏；小样本群体抑制或合并展示，
  不得反推出个体或敏感资源。
- R-FAIR-4：度量结果可下钻到贡献了该聚合数字的申请版本集合（对有权运营人员），
  支撑"公平开放目标在不同群体中的实际达成情况"的回答。

## 11. 资料版本

本规则在领域资料 `fixtures/context.json` 中为 version 2；version 1 事实保留不改。
任何后续修改只能以更高版本追加。
